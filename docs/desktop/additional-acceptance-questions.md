# Proposed additional desktop acceptance questions

October 18, 2026. These questions supplement the user's existing platform and workspace-agent requirements. They are proposals for review, not an automatic expansion of the active goal. The original requirements remain intact. Platform parity comes before further workspace-agent expansion.

| Additional question | Observable pass condition |
| --- | --- |
| What happens if Agentopia crashes, Windows restarts, or the connection drops during work? | Saved messages, drafts, completed tool receipts and goal state survive. Interrupted or uncertain operations are identified. Restart does not silently repeat a model request, file change, upload or external action. Recovery is demonstrated against the installed application. |
| Does Stop do what the user expects for the parent, background children and queued messages? | The interface states what will stop and what will continue. Cancelling work interrupts its owned tools and pending reviews, preserves completed results, and prevents a queued message or child report from unexpectedly restarting cancelled work. Independent background children follow their explicit controls. |
| Can the user leave a chat and return without losing their place or draft? | Concurrent chats keep their own drafts, selected provider/model, attachments, queue and active request. Navigation does not cancel independent work. Reading an earlier message is not pulled to the bottom by streaming; returning to latest resumes following. Long conversations remain usable. |
| Are conversation history, project context and agent memory kept within their intended boundaries? | Separate accounts cannot read each other's chats, attachments, provider credentials or memory. Project isolation and disabled memory remain enforced. Cross-chat reads obey the intended scope and retain citations so the user can inspect their source. |
| Does changing or revoking permission take effect during running work? | Removing a file/window grant, disabling a plugin, retiring an agent, changing account or reducing permission prevents subsequent actions by the parent and children. Existing completed results remain inspectable. Permission changes cannot be bypassed through another tool or a queued request. |
| Can hostile content in a webpage, file, plugin result, image or child report redirect the agent? | Such content is handled as reference material. It cannot grant permission, impersonate a user instruction, obtain another account's data or authorize an external action. Representative malicious fixtures exercise the actual tool path. |
| Does the agent accurately describe what it did? | Claims of creating a file, running a command, sending a message, scheduling work or finishing a goal correspond to saved successful tool results. Failed, denied, cancelled and uncertain outcomes are shown accurately. Proposed work is distinguishable from completed work. |
| Are the selected connection and model used consistently, with understandable cost and limit behavior? | New chats honor the saved default; explicit selections and saved conversations retain their connection. Unsupported tools, unavailable models, expired authorization and usage limits produce actionable errors. The system does not silently switch to a paid provider or duplicate an uncertain request. |
| Do generated files work outside Agentopia? | Representative Word documents, PDFs, spreadsheets, presentations and images open in independent readers. Text, layout, images, formulas, notes and links are checked as appropriate. The file linked in chat is the actual saved output and remains available after reopening. |
| Do schedules behave predictably across time zones, restarts and missed runs? | Local-time and daylight-saving behavior is visible and tested. The product explains whether work runs while the window is closed or Windows is asleep. Missed-run policy is explicit, runs are not duplicated, failures are inspectable, and pause/edit/delete prevents later unintended execution. |
| Can a new Windows installation work without the source checkout or development tools? | A supported clean Windows machine installs and opens the app with its declared prerequisites. Bundled runtimes, tools and document capabilities work without a development server, separate Node/Python/Codex installations or machine-specific paths. |
| Can an upgrade fail without trapping or losing the user's data? | A verified backup can be restored. Failed migrations leave an understandable recovery state. Accounts, passwords, native sessions, chats, agents, plugins, attachments and selected external folders have an explicit preservation or backup policy. Unrelated WSL environments stay unaffected. |
| Can people use the interface with the keyboard, larger text and different window sizes? | Core actions have useful accessible names, visible focus and keyboard paths. Menus close predictably, dialogs return focus, and narrow panes or Windows scaling do not hide Send, Stop, model, queue, goal or permission controls. Light/dark and larger-text layouts remain readable. |
| Does the app remain useful without internet access? | The app opens its local account, history, files and agent settings. Features requiring an online service say so clearly and recover when connectivity returns. Local work is not discarded or repeatedly submitted while offline. |
| Can a user understand and diagnose a stalled goal or background task? | The interface distinguishes working, waiting for the user, paused, disconnected, failed and complete states. It exposes recent confirmed activity, elapsed time and useful next actions without presenting unsaved reasoning as a work log. A goal does not spin endlessly without meaningful progress. |
| Can diagnostics be shared without revealing secrets? | Logs and diagnostic exports omit tokens, API keys, password material and unnecessary private content. Errors still identify the failed component and operation. A user can inspect what is being exported. |
| Can two agents work on the same project without overwriting each other's changes? | Concurrent file edits detect changes made since the file was read. Conflicts are surfaced with a reviewable comparison. Separate workspaces remain separate, and a child cannot overwrite a parent's newer work silently. The same checks apply to commands that modify files. |
| Do queues and goals remain predictable when controls are used quickly? | Repeated Send, Steer, Pause, Resume and Stop actions do not create duplicate turns or lose messages. Queued entries can be inspected, edited and removed before dispatch. A pending goal continuation waits for queued user work according to an explicit ordering rule. Tests cover a response finishing at the same instant a message is submitted. |
| Can a goal distinguish success from waiting, failure and lack of progress? | Completion is tied to the user's acceptance conditions and supporting results. Missing credentials or required user input produce a waiting state with an explanation. Repeated unchanged failures produce an actionable stalled state. An unbounded goal still allows prompt pause, cancellation and review of its activity. |
| Do skills and plugins actually change the agent's available behavior? | An installed skill is discovered in its intended scope and its instructions are used on a representative task. Enabled plugin tools are available to the correct agent; disabled tools disappear from subsequent execution. Invalid manifests, unsupported versions and missing dependencies give useful errors. Updates preserve user settings and identify permission changes. |
| Can the user inspect and correct what an agent remembers? | Saved memory can be viewed, corrected and deleted in its intended agent/project scope. A later chat demonstrates an approved correction and stops using a deleted record as stored memory. The interface explains that older conversation text can still contain the original information. Provenance identifies where saved memory came from. |
| Does delegated work reach the right parent without repeated reports? | Children retain their instructions and identity, continue according to their background-work setting, and report a result once to the intended parent. The parent can cite the child's result and acknowledge failures. Restarts, repeated notifications and simultaneous completions do not create duplicate reports or restart cancelled parent work. |
| Can the user review and recover agent changes? | File changes show the affected paths and a readable comparison. Review detects changes made since the proposal was produced. Recovery restores the intended prior version without overwriting newer unrelated edits. External actions identify their destination and outcome; actions that cannot be undone say so before execution when review is required. |
| Are capability differences visible before the user starts work? | The chosen connection and model expose only supported thinking levels, tools, image input and other capabilities. The interface explains unavailable features and offers an explicit choice of another configured model. Using the actual Codex harness is verified separately from each model's demonstrated ability to use it. |

## Suggested priority

Before declaring the private Windows release ready, prioritize interruption/restart recovery, Stop semantics, account/project isolation, immediate permission revocation, truthful tool outcomes, provider/cost behavior, independently usable artifacts, schedule semantics and recoverable upgrades. Continue visual and keyboard comparisons throughout implementation.

## Practical release questions

Use these questions to organize the acceptance run around the user's outcome:

1. Can I give an agent a real task, leave it working, and return to a usable result with evidence of what it did?
2. Can I interrupt, queue, steer, pause or stop work without losing messages or causing duplicate actions?
3. Can I trust the account, project, agent and permission boundaries while several chats and children work at once?
4. Can the agent use the required files, browser, commands, skills and plugins through the selected connection?
5. Can I understand a failure, recover from a restart and restore my installation without losing my work?
6. Do the visible controls and their complete interactions match the observed reference, with remaining differences documented?

For each run, choose a concrete task and expected output before testing. Record what the agent may do autonomously, where user input is required, which connection is selected and what recovery will be tested. A successful greeting or isolated tool call does not establish completion of that larger workflow. Use ChatGPT OAuth for routine live runs and inspect existing outcomes before issuing any additional paid request.

These are verification questions. Existing historical test results retain their original version and scope. A passing component test does not establish a live provider result or a clean-machine installation. ## Recommended acceptance gates for the goal

Use the following existing requirements and additions as the first release gates. Define the expected output and evidence before each run. These gates organize the checklist; they do not mark any requirement as passed.

1. **Complete useful work:** give the agent a realistic task requiring inspection, tool use and a saved output; verify the output independently and check its source links.
2. **Keep control during work:** queue two follow-ups, explicitly steer one, revise the goal and exercise pause, resume and Stop while children are active. Verify ordering, the latest instructions and the lifetime of owned work.
3. **Survive interruption:** interrupt a request and restart the packaged application. Recover drafts, history, goals and child results, while retaining uncertainty about any action whose outcome is unknown and avoiding duplicate execution.
4. **Respect scope:** run concurrent accounts, projects and agents, then revoke a relevant permission. Verify that subsequent actions obey the change and that other work remains unaffected.
5. **Keep connections predictable:** use ChatGPT OAuth for routine live work; verify explicit model changes, context continuity and unsupported capabilities. Reuse valid OpenRouter evidence and reserve additional paid checks for connection-specific behavior.
6. **Deliver the installed experience:** compare the full reference interactions at comparable display settings, exercise supported voice hardware, and verify usable artifacts and recovery without a source checkout or development server.

Record workspace-agent identity, private memory, procedures and coordination as the next acceptance stage after the platform gates, following the existing sequencing decision. Preserve their requirements in the goal throughout.

## How to accept a requirement

For each approved requirement, record the user action, expected visible behavior, permission and provider setup, application version, observed result and evidence location. Include both a successful case and the relevant interrupted, denied or invalid case. Mark source implementation, controlled tests, installed-app verification and live-provider verification separately; only claim the level actually demonstrated.

For visual parity, pair a current ChatGPT/Codex Desktop reference capture with an Agentopia capture at comparable window size, theme and text scale. Compare the complete interaction, including focus, keyboard controls, loading, errors and returning to the chat. A matching screenshot alone does not establish matching behavior.

Routine live checks use ChatGPT OAuth. OpenRouter live checks are reserved for behavior specific to that connection, with completed or uncertain requests inspected before another request is sent.
