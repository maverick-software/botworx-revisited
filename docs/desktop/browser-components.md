# Browser controls inside web components

October 17, 2026. Installed release 0.43.2 passes the source and packaged Chromium checks, actual native-provider workflows, Windows upgrade, data preservation, and normal desktop cold launch. The broader desktop parity goal remains active.

## Finding and behavior

The embedded browser already exposed web-component controls in its accessibility snapshot, but input validation assumed that the target lived directly in the page's document. A shadow root is the separate DOM tree used by a web component. The document reports the component host when checking focus or the element at a point. That caused valid component text entry and key input to fail focus checks, while buttons containing child text and component dropdowns could be reported as covered.

A Chromium reproduction recorded six failures in the previous implementation while the ordinary document button and accessibility discovery passed. The correction follows the composed DOM tree: the rendered relationship between ordinary elements, slots, shadow roots, and their containing hosts. Hit-testing checks the target within its root and then every containing host. Focus validation follows the same chain to the outer document. The checks execute in the existing isolated browser world, so a website's replacements for DOM methods do not override them.

Reference-based browser clicks, filling, native dropdown selection, and declared keys now operate on visible controls in ordinary, nested, slotted, and closed web components. Closed components are addressed through the existing Chromium accessibility/DOM references; this adds no page-script execution tool. Existing site-sharing reviews, ownership, mode restrictions, changed-target checks, password/payment restrictions, unique input receipts, and uncertain-input handling continue to apply.

## Checks and limits

After `npm run desktop:build`, `npm run desktop:test:browser-shadow` starts real Electron/Chromium with controlled component pages. All 15 scenarios passed in the source engine and again using the actual installed modules. They verify ordinary document input, accessibility discovery with private input values omitted, exact text changes, nested and slotted buttons, a closed component button, dropdown selection, and trusted Enter input. Additional cases check nested and closed component text fields, overlays inside and outside components, successful operation after page-prototype replacement, and focus redirected when a control receives focus. The latter verifies that protected contents remain unchanged in those cases. Existing ordinary-browser and form-input workflows also passed.

The `--baseline` mode records the expected failures using an earlier compiled module directory. `AGENTOPIA_BROWSER_MODULES` selects that directory, and `AGENTOPIA_BROWSER_SHADOW_OUTPUT` selects a fresh evidence directory. Reusing a completed evidence filename is refused. These tests use actual browser execution and make no model request.

`scripts/desktop/test-live-browser-shadow.mjs` is the separate installed-model check. It uses a temporary debugging connection to the actual installed app and switches providers through the composer in the same conversation. The controlled website independently checks the cookie, retained field value, exact region, trusted click/Enter events, and one submission per provider. It returns unpredictable receipts for the agents to report. Before the provider switch, the controlled page removes the first receipt and acknowledges that removal; the second provider must recover it from the conversation. Request identifiers and dispatch checkpoints are saved before any additional work; earlier requests must never be replayed after an observation failure. Select a fresh `AGENTOPIA_BROWSER_SHADOW_LIVE_OUTPUT` for a new workflow; `AGENTOPIA_BROWSER_SHADOW_FIRST_PROVIDER=openrouter` chooses the opposite provider direction.

The first ChatGPT turn successfully clicked a nested component, selected East, filled the component message, submitted one trusted Enter, and reported the independent website receipt. Before the second Send click, a progress-file reader briefly prevented Windows from replacing the verifier's metadata file. The verifier stopped and its cleanup closed the controlled tab and restored the original chat. Read-only inspection confirmed the completed first turn, its receipt, and the absence of a second submitted request. That completed turn was retained rather than repeated.

The checkpoint writer now serializes complete snapshots and retries only temporary metadata replacement failures. A regression holds a real Windows file handle without delete-sharing, confirms replacement is blocked, checks the queued snapshot, releases the reader explicitly, and verifies the final saved state. This focused check passed in addition to all 240 prior desktop regressions. No product binary changed during this verifier repair.

A separate new OpenRouter-to-ChatGPT pair then passed. OpenRouter completed the nested component click, dropdown and text-entry workflow. ChatGPT continued in the same live tab, clicked the closed component, changed the dropdown, retained the existing message, and submitted Enter. Saved messages remained unchanged after renderer reload. All three completed real chat turns use the actual Codex 0.163.0 harness with GPT-6.1 Sol at High; these are chat turns, not a count of the provider's underlying HTTP requests.

This change covers controls reached through the current page's existing references. It does not establish general iframe support, additional file-input discovery inside component trees, directory uploads, custom native chooser interception, personal Chrome consent, or complete desktop parity. Those remain separate parts of the overall goal.
