## Broker, steering and user controls

Authorized handoffs share the existing FIFO queue with user messages. The coordinator serializes operations on a delivery, retains its identifier across queue persistence, and reloads the database record before dispatch. The broker reserves the receiving conversation before claiming the handoff. It loads only the intersected files, atomically prepares the receiving request and inherited agent instance, and enters its actual Codex execution path. The human chat's original agent instance and composer preferences are retained. A delivered receipt acknowledges acceptance of the message; the receiving chat records task completion separately.

Native steering resolves the exact current receiving request and turn, checks its actual options and agent policy after asynchronous reads, and binds that request before calling Codex. A running turn with broader command, file, window, skill or tool access cannot accept the message as steering. Source cancellation is checked after the saved claim and again immediately before the native request. A known refusal before submission cancels the handoff and clears its receiving dependency without stopping that chat. Once native submission is attempted, an uncertain acknowledgement holds the message for inspection and stops the affected receiving turn. It does not replay the send. A queued message explicitly steered by the user reports its actual delivery mode in the saved receipt.

Received messages, queued handoffs and native steering activity show a compact sender link to the originating message. Incoming text retains its sender attribution and is read-only; ordinary queued user messages retain editing and removal. Waiting authorization can be answered in the receiving queue using the same once/pair/deny controls. Never-dispatched messages with valid authorization can resume after recovery. Uncertain sends offer no automatic retry or fresh authorization. Sending entries expose Stop against the actual receiving request.

Settings → Tools & credentials includes chat coordination permissions, with both chat titles and a Revoke action. Revocation holds queued work and stops dependent preparation, receiving inference, named assignments and native background work. Completed child results remain completed. A retained old context cannot stop an unrelated newer root merely because both used the same native worker.

Migration63 captures delivery dependencies when each message is prepared. This permits two running chats to exchange successive messages without validating an old receipt against a later incoming message and creating a recursive cycle. Dependencies propagate to relays and named assignments. A stopped child cannot dispatch its saved message merely because its parent is still running. Existing per-request message, destination queue and delegation-depth limits continue to apply.

## Inline review and receiving-turn checkpoint

The actual ToolService now prepares a delivery, publishes its inline review after registering the decision waiter, and saves a one-time or chat-pair decision before invoking a receiving-queue handler. `tools.decide` accepts the pair option only for an approved coordination review belonging to that account. Full access does not impersonate this first coordination authorization. An existing valid pair skips another review. Exact tool-call replay returns the saved receipt; changed text cannot reuse that identifier, and a duplicate existing outbox record does not invoke the receiving handler again.

`ChatDeliveryReview` renders the destination, sender, connection, model, delivery mode, effective permission and exact message inside the existing tool activity. Its actions are **Don't send**, **Send once** and **Allow these chats**. OpenRouter cost information appears for that connection. The review uses the existing inline interface and introduces no attachment-sharing dialog. Long text scrolls independently and the choices wrap in narrow panes.

`desktop_begin_delivered_chat` prepares the receiving request, message attribution and inherited agent instance in one transaction after a valid outbox claim. It retains the receiving connection and model, rejects broader files/windows/tools/skills and leaves the human chat's root instance unchanged. A repeated preparation returns the same request. The inherited authority chain records the specific delivery authorization; validation reaches named descendants without permanently blocking later human work or a fresh authorized handoff that reuses an instance.

Receiving project context contains only the shared files. Subsequent coordination clamps project file IDs to that inherited selection, preventing excluded target-project attachments from reappearing during a relay. The snapshot retains the human-selected recipient options separately from automated turns. ToolService validates incoming delivery dependencies before execution and again when resuming an operation after review, when a broker handler is configured.

## Implemented and checked

`desktop/src/chat-delivery.ts` defines the delivery service, a model-facing `send_message_to_chat` schema, saved sender attribution, and the permission intersection for a receiving turn. `desktop/database/0061-chat-delivery.sql` adds a durable outbox and user-authorized chat-pair records. The service's operations prepare, authorize, claim, complete, hold, review, cancel and recover a handoff. These operations do not perform inference themselves.

Preparation binds the actual account, source request, project and native thread supplied by the trusted broker. The model supplies the destination, text and optional delivery mode. Queue is the default. The model cannot supply an approval, account, permission grant, replacement provider or sender identity. A stable tool-call identifier returns its existing record on repeated delivery attempts; reusing it with different text or a different target fails.

The first send requires a trusted user decision. Inline controls offer one message, coordination in both directions between the two chats, or denial. A saved pair authorization is tied to the chats' current projects and can be revoked. It permits coordination while preserving the narrower tool and file scope. It does not turn another agent's content into a human instruction or permission grant.

The receiver retains its configured connection, model and thinking level. Shared file references, windows, selected tools and selected skills are intersected. The target's agent policy is intersected with the sender's policy. Sending is unavailable in Plan mode, Chat only and Selected files, and respects the named agent's memory, delegation, tool allowlist, allowed specialists and depth limits. Stopped goals and changed agent/project definitions invalidate the saved authorization context. A completed sender can leave explicitly authorized work queued; a cancelled root cannot dispatch fresh work afterward. An owned native child can prepare a message after its parent finishes.

Steering needs compatible current permissions because an already running native turn cannot have its capabilities narrowed by an incoming message. The service rejects incompatible steering and asks for a fresh queued turn under inherited permissions. It does not silently change the requested delivery mode.

Claims are serialized for the same message and destination chat. Queued records preserve order. A completed handoff needs the actual receiving request in the intended chat; this confirms delivery, not task completion. Restart holds pending and uncertain records. Never-dispatched authorized work can be explicitly resumed. A never-dispatched message that still needs consent can return to review, including after its sender completes. A record whose dispatch began cannot be automatically replayed or reopened for approval as a fresh send.
