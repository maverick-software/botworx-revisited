# Statistics refresh after database restoration

October 20, 2026. The fresh runtime test exposed a startup failure after the logical database import had committed. The disposable backend contained both accounts, all 124 public tables and its completed import journal. The data API repeatedly timed out while loading its schema cache. The import subprocess reported failure during its subsequent service restart.

The restore path did not refresh database planner statistics after loading the saved schema and records. PostgreSQL recommends ANALYZE after restoration so the optimizer has useful statistics ([PostgreSQL 17 pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html#APP-PGRESTORE-NOTES)). PostgREST builds and caches database metadata through catalog queries ([PostgREST schema cache](https://docs.postgrest.org/en/v16/references/schema_cache.html)).

Two startup attempts on the restored copy failed. A single-variable probe then ran ANALYZE on that same disposable database. It completed in 9.6 seconds, startup returned success, and all six core services became healthy. A read-only audit matched all 126 saved tables and 1,743 rows, all 69 migration checksums, 191 readable vault records and four encryption-root bindings. A generated account also completed password sign-in and sign-out; after its removal, the original table fingerprints still matched. This evidence supports stale planner statistics as the cause of the observed schema-cache timeouts; a new import with the correction is the next acceptance test.

The source fix runs ANALYZE after the import transaction and before stopping services to publish the restored encryption root. It also runs when resuming an already committed import, without replaying the import transaction. Four tests execute the actual Python import branch with generated processes/files: new import ordering, committed-import resume, statistics failure preserving the root/services, and import failure preventing later steps. Three cases failed before the correction; all four pass afterward. The four existing snapshot tests also pass.

Initial failure, protected diagnostics, statistics probe and generated-account evidence are in `.supabase/desktop-layout-fresh-runtime/1792524017111`. This is a disposable test runtime stored on F:. No production database, account, provider connection or installed application source was changed. The responsive UI correction remains separately prepared and awaits normal Agentopia closure.

The subsequent empty-runtime run (`1792524517711`) still failed, so statistics refresh alone did not prove recovery. A diagnostic run retained the actual private command output: PostgreSQL refused a leftover `postmaster.pid` pointing to process 83. That process was absent. The record named the exact disposable data directory. Retiring that one verified stale record, without another statistics change, allowed all core services to start. The failure and both single-variable probes remain retained.

The source now includes `database_state.py`, sent to the private runtime before startup and bundled by the build. Startup runs it as the database's ordinary Linux user. It selects only the saved default Agentopia project, verifies the directory/control file/version, checks that the recorded process is absent and `pg_ctl status` reports stopped, then checks that the record did not change before retiring it. Live, linked, mismatched, changed or ambiguous records remain preserved or cause refusal. The import shutdown barrier uses the same check before replacing the encryption root. Six generated cases verify dead/live process behavior, controller states, directory mismatch and concurrent record changes. The combined source qualification now passes 57 direct Python cases, plus the earlier 177 JavaScript, 48 PowerShell and five Windows PowerShell 5 cases. A new empty-runtime run with both corrections remains the required next proof.

The next run (`1792525174660`) captured the original import error directly. PostgreSQL refused startup because old server workers were still attached to its shared-memory segment after the main process had stopped. Production and the disposable runtime have different IPC namespaces, so this was inside the restored test runtime. Checking only `pg_ctl status` and the main process record was insufficient.

The next source revision captures the shared-memory identity before requesting shutdown, then waits for its worker attachment count to reach zero before retiring a stale process record or publishing the restored encryption root. It never removes shared-memory segments. Timeout preserves the root and reports that workers are still stopping. Ten generated database-state cases now cover attached/detached workers and the actual shutdown barrier's wait/timeout behavior in addition to the earlier cases. Complete source qualification and another fresh import/cold restart remain pending for this revision.
