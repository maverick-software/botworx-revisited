# Inline goals and queued messages

Updated October 18, 2026. Version 0.44.17 is installed on this computer.

Choose **Goal** from the composer’s Add menu, type the objective in the ordinary message field and send it. This creates a goal with unlimited turns and no token budget. The first saved user message contains the objective itself. The goal strip above the composer shows its status and a shortened objective, with delete, edit, pause/resume and expand controls. Edit and expand open a Goal tab beside the chat. There is no goal creation modal or turn-limit field. Plan implementation also creates an unlimited goal; its existing implementation review remains available.

Pause disables automatic goal continuation while allowing the current response to finish. Stop response interrupts that response. Editing an active goal pauses it, waits for the owned response to finish and saves the revised objective. Resume is explicit. Deleting a goal preserves the conversation. Provider usage limits, errors, work requiring user input and completion can still stop progress. Existing saved goals retain their previously authorized limits until edited or explicitly resumed through the new interface. Resume removes the former allowance before starting work.

While a response is working, Enter or **Queue** stages the new message above the composer. It does not change the current turn. Queued messages retain their chosen connection, model, thinking level, permissions and selected context. They can be edited or removed. After a successful response, the broker sends the next queued message in order even if the user has switched to another chat. Another chat’s work can continue independently.

**Steer** is an explicit alternative, available both beside the composer and on a queued message. It targets the exact active native turn. A failed or stale steering operation retains the unsent text. Existing file and window context can be reused; newly added context needs a queued turn. Both ChatGPT OAuth and OpenRouter retain their native Codex execution path.

Queue records are stored in the existing Windows-encrypted, account-scoped local store. Restart, failed responses and interrupted sending hold the queue for review. An accepted or uncertain request retains its identifier, which prevents a retry from becoming a second model request. Storage failures hold the queue visibly and prevent repeated attempts.

The preparation race discovered during live workspace-agent verification is also corrected. A delayed goal or completion event from an earlier warm-thread turn could resolve a new execution before it started. The harness now reserves ownership during preparation and buffers turn events until the new turn identifier is acknowledged. Only events belonging to that turn are replayed. Four controlled regressions reproduce the failure against the earlier packaged backend and pass with the correction.
