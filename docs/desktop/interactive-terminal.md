# Interactive terminal workspace

Version 0.17 adds persistent Windows PowerShell sessions to the existing right workspace. The application rail, chat/project sidebar, folder tree, document/editor/plan tabs and browser/canvas remain independent navigation surfaces.

Choose **Terminal → Interactive session**, select a starting folder, enable Windows commands if necessary, and choose **New session**. Click the terminal to type. Programs can ask for input, variables and the current directory persist between commands, and Ctrl+C or **Interrupt** interrupts the foreground program. **Stop session** ends the shell and its managed descendants. Closing a tab or reloading the interface keeps a live session running. Its selector reopens saved output. A stopped session is a transcript; opening it does not rerun commands or restore process memory.

The starting-folder controls follow the selected workspace root until a different terminal folder is explicitly chosen. **Use workspace folder** resumes following the root. This also applies to the existing noninteractive **Commands** view. Changing the folder selector does not move a running shell; use a shell command to change its directory or start another session.

## Providers and permissions

Both providers use the same `workspace` tools: `start_terminal`, `write_terminal`, `read_terminal`, and `stop_terminal`. Under Default permissions, the initial command and subsequent agent input each wait for review of the exact source/input and working directory. Full access uses the existing explicit native confirmation. Reads and stopping an owned agent session do not require another command approval. A denied operation cannot be retried by changing its explanation or output-wait duration. Stable provider call identifiers prevent repeated mutations within a request.

Agent tools can access only agent-started sessions in the same conversation and a currently selected folder. A manually opened session is not automatically supplied to the model. Its output stays outside AI requests unless the user explicitly shares it or shares files created by it. Provider input and output are retained as tool receipts in the conversation. Terminal output is untrusted source material. A running shell does not prove that its foreground command finished; a shell exit code describes the shell. Report command completion from its actual output and relevant checks.

Sessions require an Agentopia administrator and enabled Windows commands. They run under the Windows account with its filesystem and network privileges, including outside the starting folder. This is not a filesystem sandbox. Standard Agentopia users cannot start, enter, resize, or retrieve host sessions; direct authenticated database access requires ownership and the administrator role. Commands and sessions share a limit of three simultaneous processes per account, including launches in progress.

Role loss, revoking Windows commands, sign-out, account changes, app close, and deleting the linked conversation stop managed sessions. Cancelling a response stops sessions started or entered by that active response. Cancelling a read alone leaves an existing background session running. A completed turn may leave its session running for later input; stopping it is explicit. Pausing/completing a goal or reaching its turn limit stops that goal's background sessions. Direct human input clears the session’s assignment to a prior background goal; cancellation of an active response can still stop a session it started or entered. Sessions also stop after 30 minutes without input. Prior effects, external services, elevated or detached processes, and Linux work launched through WSL can need separate inspection before retrying uncertain work.

## Delivery and recovery

The bundled supervisor uses Windows' native pseudoconsole with separate threads for input reception, pipe writing and output reading. It joins a Windows job before launching the shell. The parent-owned input pipe is a lease: losing it after an abrupt app-process termination ends the job. Explicit null child standard handles keep the shell out of that control pipe. [Microsoft pseudoconsole guidance](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), [redirected-parent handle behavior](https://github.com/microsoft/terminal/discussions/15814).

The renderer uses bundled xterm.js with no Node.js privileges, external-link opener, clipboard escape handler, or window-operation permissions. Output is rendered as terminal text. Recognized credential patterns are redacted and terminal operating-system-control sequences are removed before publication. Provider credentials are excluded from the shell environment. Pattern matching is not a general guarantee against exposing sensitive material; users must keep secrets out of host commands and interactive input. [xterm.js security guidance](https://xtermjs.org/docs/guides/security/).

PowerShell starts without profiles. Its line-editing history is kept in the session, with an unused session-specific history path and `SaveNothing`; the Windows user's shared PowerShell history is not imported or appended. This uses process-local settings and leaves the user's normal shell settings unchanged. [Microsoft history settings](https://learn.microsoft.com/powershell/module/psreadline/set-psreadlineoption).

Output is saved to PostgreSQL in bounded batches, including a final scheduled flush when the program becomes quiet. The latest 200,000 characters are retained; excessive output stops the process after four million characters. Text input chunks are bounded. Recognized credential text adjacent to ANSI colour codes is also redacted. Account-owned logs retain status, output, revision, timestamps and shell exit information. Startup marks formerly running sessions Interrupted and retains acknowledged output. It never starts the old shell or replays old input. Applied migration 0022 adds the session table, own-admin read policy, and mutation-identifier index without rewriting earlier migrations.

The noninteractive command path now also retains its actual partial output in an interrupted tool receipt, so later provider history can distinguish cancellation and an unconfirmed exit from successful completion.

## Verification boundaries

Native-process tests cover retained state, prompted input, resizing, real exit codes, environment filtering, ANSI/redaction, unchanged Windows shared history, and cleanup of a shell and normal descendant after a parent-only kill. Database/provider tests use controlled inference to drive real Windows sessions, approval/denial, cross-provider continuation, duplicate prevention, conversation/account/role restrictions, capacity, goal limits, and partial-output receipts. A controlled progress source additionally verifies that the last quiet output batch is saved.

Desktop tests exercise actual keyboard input, workspace-folder following and explicit choices, reload without restarting the shell, provider handoff, review, manual-output privacy, saved transcripts, and forced-termination recovery. Separate live-provider and installed-package checks are recorded in the implementation status; controlled inference is not evidence of live provider compatibility.

Further work includes explicit adoption/sharing of manual sessions, persistent terminal form/mode selections, additional shell profiles, broader Windows keyboard/input combinations, terminal splits, restoration of a terminal screen after output truncation, and further accessibility and physical-device testing. Full application parity remains tracked in the parity backlog.
