The cause is a contract mismatch. `chatDeliveryScope` deliberately clears selected browser/chat snapshots with `sources: []`. Its receiving service serialized that empty UI field into a database function whose strict execution-options allowlist predates it. PostgreSQL rejected the receiving request before creation. The previous controlled broker tests did not connect this serialized payload to the real receiving SQL, which left the mismatch undetected.

The repair leaves scope calculation unchanged and omits the empty `sources` field only at the receiving RPC boundary. A guard rejects a future nonempty selected-snapshot payload there. The SQL allowlist, owned-chat rules, inherited file/tool ceilings, target connection and duplicate-preparation checks remain enforced. The regression test reads the actual database allowlist and covers empty and populated selected snapshots without mutating the originals. It reproduced the failure against the delivered64 module before the fix. All 76 delivery, queue, native-policy and permission checks then passed. Source qualification: `F:/Agentopia/.supabase/desktop-chat-delivery/check-1792644918719/evidence.json`.
