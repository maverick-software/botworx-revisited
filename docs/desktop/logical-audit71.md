# Streaming logical recovery audit for schema 71 and later

The accepted69/70 maintenance paths retain their original audit and hashes. That audit expects the126 application/account/vault tables in its pre70 snapshot. A fresh70 snapshot has127 because it includes desktop_media_files. The new audit-production-logical71.py compares a fresh backup with the live database without hard-coding the table count.

Coverage is explicit: every non-extension-owned public application table, auth.users and vault.secrets. The live application-table list must match the decoded archive's list, so an omitted application table fails the audit. Account IDs must match the snapshot manifest. Password and role data are compared; last_sign_in_at and updated_at in auth.users are the only ignored columns. Other authentication runtime/session tables are outside this row comparison. Vault readability and all four encryption-root bindings are checked separately.

Rows stream from pg_restore and one repeatable-read, read-only database transaction. Each complete COPY row is hashed. SQLite stores and orders only those row hashes; duplicate multiplicity is preserved. The final table fingerprint includes row counts and ordered column names. The audit never accumulates the complete decoded dump, including original bytea payloads. A row over 64 MiB or malformed/incomplete framing fails explicitly. This supports the 20 MiB original-file limit while keeping large collections out of one Python string.

Ten generated-data cases cover row reordering, duplicate loss, original-byte changes, password/role changes, sign-in timestamps, escaped fields, malformed/incomplete/oversized COPY input and 512 MiB of streamed payload. The measured peak traced Python allocations for that generated stream are about 2.1 MiB, below the 8 MiB test ceiling. That measurement excludes SQLite/native allocations and child processes; SQLite's cache is limited separately.

The full audit passes against an owned restored QA database with 127 tables, 89 selected saved rows and three retained originals. QA services are started and stopped only for that test. A fresh read-only production comparison passes all 127 tables and 1,808 rows, including two accounts/passwords/roles, 120 chats, 410 messages and 191 readable vault records. The ordinary application stays open, its data is not changed, and no provider request is made.

Qualification pointer: `.supabase/desktop-logical-audit71/qualified-current.json`. The receipt binds source hashes, unit evidence, the QA result and the fresh production snapshot/audit. The new auditor is available for the next maintenance controller; do not alter the historical69/70 helpers to substitute it retrospectively. Future source snapshots must use this schema-aware path so original and revision tables are included. Observation failure alone never permits terminating a QA runtime; its controller requires the completed service-stop receipt first.
