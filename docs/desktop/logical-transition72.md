# Preserving rows during the71-to72 schema transition

The ordinary 0.44.70 database has 127 table comparisons: every non-extension-owned public application table, auth.users and vault.secrets. Migration72 adds desktop_media_revisions. The new transition comparator checks every prior row and explicitly verifies that this sole new table is empty, has the expected columns and primary key, uses row-level security, denies anon/authenticated access, permits the service role, and keeps the management functions broker-only. Unexpected missing/additional tables, other schema versions or access drift fail acceptance. Existing strict auditors and accepted69/70 maintenance helpers remain unchanged.

The implementation is audit_logical_transition72.py and reuses the qualified streaming row-fingerprint engine. No complete decoded dump is buffered. Rows retain duplicate multiplicity; password/role fields are compared, and only the documented volatile account sign-in/update timestamps are omitted. Four encryption-root bindings and readable vault counts must match. audit-maintenance-logical71.py selects the strict same-schema comparison before installation and the transition comparison after the ordinary app completes migration. Every invocation retains a distinct evidence directory.

Qualification: `.supabase/desktop-logical-transition72/1792754451149/qualification.json`. Fourteen generated cases verify rejection of unauthorized coverage, nonempty revisions, altered columns/keys and access changes. Five real database checks use the independently owned restored70 QA copy: a correct transition passes; a changed old agent row, a new revision row and an authenticated SELECT grant fail; all 89 prior rows and schema 71 are restored afterward. QA services stop normally. These tests make no model requests or production writes.

The first rehearsal's negative agent-row update also changed updated_at through the normal table trigger. Restoring its description alone left that timestamp different, which both comparators detected. The repair checks that exactly one existing row differs and only in updated_at, restores that timestamp from the verified pre-test COPY rows with the user trigger temporarily disabled, restores the trigger, and compares all 89 rows again. Evidence: the repair folder under `.supabase/desktop-logical-transition72/1792754195660`. The revised negative fixture isolates this trigger during its deliberate edit and restores it afterward; its final strict comparison passes. No unrelated field or customer row is repaired or ignored.

The ordinary70-to71 comparison passes against the fresh production snapshot captured after normal application closure. It matches all 1,808 saved rows in127 prior table comparisons and verifies the new empty broker-only table, for 128 covered tables. Two accounts, password/role records,120 chats,410 messages,191 readable vault records and four encryption-root bindings agree.
