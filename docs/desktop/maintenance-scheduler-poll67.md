# Workspace maintenance and scheduler polling — source67

The real PostgreSQL acceptance run exposed a maintenance failure in the first 0.44.67 candidate. Workspace archival was admitted while the application was idle, then failed during repeated ownership/activity checks. The ordinary 0.44.66 installation and its data were not changed.

An observation-only wrapper recorded the actual Broker activity flags in the isolated packaged app. At the rejected check, every activity count was zero except `scheduled.scheduler.busy`; the backup and storage-maintenance barriers were both active. The scheduler's five-second timer had entered its database poll during the capture. Polling counts as busy because it can stage or claim a scheduled run, so the capture correctly rejected that overlap. The missing part was preventing the timer from entering after maintenance had already reserved the application.

The Broker now supplies a `canPoll` predicate to the scheduler. It is false for the complete backup/maintenance interval. The scheduler checks it before reserving a poll and again before continuing database work. This keeps the existing admission checks for a poll, task claim, queued dispatch, active agent, chat and terminal. Normal polling resumes after the maintenance barrier is released, including when a capture fails.

The regression uses the actual Broker backup barrier and actual TaskScheduler with controlled database methods. Before the fix, a poll reads the database inside the reserved capture and the test fails. With the fix, it performs no reads and does not become busy during capture; the next permitted tick reads normally. The maintenance/scheduler suite passes 20 cases. The desktop admission, close, editor and storage suite passes 41 cases. The suites overlap and their counts are not combined.
