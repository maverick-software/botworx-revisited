# Native child recovery and PostgreSQL policy ordering

An actual independent Codex child remained running after its parent finished in the frozen27/schema69 Windows application. A test-driver callback error stopped observation before any child image request was dispatched. The completed parent image and saved child were retained, and the app closed normally.

Reopening the same native profile correctly retained the image and interrupted child without inference replay, but explicit child resumption failed with “The agent definition changed.” Read-only inspection of the real PostgreSQL records found matching definition revision3, memory revision0 and every policy value. PostgreSQL JSONB had changed the order of policy fields. The current policy was validated into a fixed field order, while the saved context remained in database order. Comparing their JSON text produced a false change, and would also have changed the native configuration fingerprint if passed through unchanged.

The broker now validates the saved policy through the existing `agentPolicy` parser before comparing it or restoring execution. It preserves all existing revision, memory-revision, ownership, assignment and native scope checks. No database migration or stored permission modification is needed.

Twelve regression checks round-trip a policy through embedded PostgreSQL JSONB, then exercise the public broker child-control restoration path. The unchanged reordered snapshot must restore; changes to each of the seven policy fields, either revision and malformed policy must still fail before native execution. The unchanged27 archive reproduces the positive-case failure; the corrected source passes all12, alongside35 image/runtime checks. Evidence: `.supabase/desktop-image-generation/recovery-red-1792369224988/evidence.json` and `.supabase/desktop-image-generation/source-check-1792369224988/evidence.json`. The real-record diagnosis is `.supabase/desktop-packaged-coordination/1792368944450/child-recovery-inspection-1792369137700/diagnosis.json`.
