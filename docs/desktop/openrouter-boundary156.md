# OpenRouter tool-call investigation

The installed application remains checkpoint155. This investigation changes acceptance scripts and reporting; it introduces no product behavior change. Reliable longer OpenRouter work remains unproven.

Run152 completed its approved calculator command, then repeatedly called process input with an invalid process identity and saved no receipt. Its original upstream stream was not recorded, so that evidence cannot establish where the incorrect function names originated. Run156 therefore used one fresh three-row invoice batch, a fresh account and goal, the installed native harness, and the same real OpenRouter `openai/gpt-5-mini` connection. It retained the required order: read the browser source, run the reviewed read-only calculator, save and read back a receipt, and close the source tab. This was a bounded diagnostic, with a ceiling of 12 provider responses and a $0.50 accounting allowance. It was not a longer-task acceptance test.

The observer records function names, namespaces, argument hashes and usage while forwarding the original response bytes. An offline check sends UTF-8 content one byte at a time, confirms unchanged forwarded bytes and checks that argument contents are absent from the metadata journal. The dispatched controller and its source hashes remain frozen with the attempt. A later local correction makes the `argumentBytes` field count UTF-8 bytes rather than JavaScript string units; the original journal remains unchanged, and neither the names nor argument hashes used in the comparison depend on that field. The corrected observer passes the same local checks without a provider call.

Run156 received 12 successful upstream HTTP responses over 58.56 seconds. The provider repeatedly supplied command attempts before the browser source had been read, along with unsupported tool choices. The existing scope guard refused premature or unreviewed commands. The model eventually opened and read the source and executed the exact approved helper. Its seven counts and monetary values matched the independently generated expectation, including a total of 3,709 cents. It saved no receipt before the response ceiling, so the task failed its acceptance criteria.

Read-only comparison matches all 12 upstream function calls to the native session by call identity and order. Every function name, namespace and canonical argument hash agrees. That establishes that the observed choices in this attempt arrived from the provider unchanged. This attempt did not reproduce the earlier invalid process-input loop, so the precise cause of run152 remains unresolved. No routing rewrite or model-name alias change is justified by these observations.

The local acceptance gateway refused further inference before external dispatch after the twelfth response. The native client reported a 502 connection failure while retrying that local refusal; all 12 actual upstream responses were successful. The goal was paused, temporary access and provider credentials were removed, and the QA application closed normally. Cold reopening preserved the paused goal and drafts, sent zero further inference requests and stopped its isolated runtime. Source CSVs and the helper remained unchanged. The ordinary profile was untouched. Recorded usage gives a published-rate estimate of $0.0137597, with zero responses whose usage remained unknown; this is not a verified provider invoice. The completed or uncertain earlier attempts were not replayed.

An additional offline check157 starts the actual bundled native harness separately with `gpt-6.1-sol` and `openai/gpt-6.1-sol`, using controlled final replies and no provider requests or real file writes. Both expose exactly the same tool schemas and a reported context window of 258,400 tokens. Their workspace-specific instruction hashes differ, so the check does not claim identical instruction text. The configured current model uses the native code-execution interface in both cases; the cheaper older mini model used for the failed endurance probes exposes a different native interface. These offline results establish catalog consistency for the two current-model names, not live current-model reliability. A properly bounded real check of the configured model remains necessary before making a broader OpenRouter autonomy claim.
