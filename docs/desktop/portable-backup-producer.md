# Portable backup producer foundation and image gap

**Current status, October 20:** portable image export/re-encryption and the normal Settings integration are now qualified in source. The installed app still uses recovery-bootstrap-15. See [current workflow, evidence and remaining acceptance](portable-backup-settings.md). The account below records the earlier foundation checkpoint and its then-open image gap.

October 19, 2026: **qualified in source, not installed or connected to Settings.** The installed application remains accepted 0.44.47 recovery-bootstrap-15. Its existing Backup command is unchanged. This work establishes the archive/bundle producer and consistent account capture; clipboard-image portability must be implemented before enabling the new product command.

The existing app backup writes database archives and raw native/workspace folders. It omits the attachment-image directory and produces a different layout from the format-2 first-start preparer. The new producer writes compressed managed/native and public archives, their inventories, the public attachment index, the restore helper and a final six-resource descriptor. It verifies archived file bytes and checks the source inventory again. Privacy is established on the new backup directory before database records are exported. Linked or redirected paths, source-overlapping destinations, changed resources, insufficient disk reserve and repeated destination names are refused. A failed operation leaves an incomplete marker and no completion descriptor. An absent public collection produces an empty archive without creating a source folder.

Database export now reads the account UUIDs from the same kept PostgreSQL snapshot used by all four dumps. The manifest includes those IDs and derives its account count from that list. This avoids deriving ownership from a later account query. The runtime has a database-only capture method for the upcoming portable command; the old backup method remains available. The broker blocks data calls during backup, prevents a new capture during scope or agent mutation, and permits a copied attachment-index read only within its backup barrier.

## Clipboard images must cross the Windows encryption boundary

`AttachmentImages.write` encrypts image data through Electron safeStorage, and `read` decrypts it through that Windows credential context. Copying those encrypted `.bin` files preserves their bytes but does not make them readable on another Windows account. The current format-2 preparation deliberately excludes the original Windows credential store. The portable image path therefore needs to export validated image pixels into the private backup, retain each owner/reference identity, and encrypt the pixels under the destination account before attachment cleanup or preview runs.

That conversion and restoration are not implemented yet. The source producer explicitly refuses a clipboard reference before publishing a completion descriptor. Its private archive also excludes opaque attachment ciphertext. This is an incomplete producer gate, not acceptance of a reduced backup scope. The goal still requires portable pasted images and the complete ordinary-user backup/restore flow. No new Backup UI or IPC action was exposed by this turn.

The next implementation should require a newer recovery capability for bundles containing portable clipboard payloads so installed revision 15 cannot silently skip them. Destination-side recovery must validate owner/ID/hash/size, detect conflicts, support interruption without overwriting an existing image, publish restored references atomically, and run before `WorkspaceFiles.recover` can remove unregistered images. Its applied marker must respect later user deletion. The new normal backup command must also flush pending edits/drafts and keep application shutdown from interrupting its archive operation.
