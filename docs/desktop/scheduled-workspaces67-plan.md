The current reference documentation explicitly supports multiple projects for one standalone scheduled task and local-project or isolated-worktree execution for Git projects. Non-Git projects run locally. Local-file tasks need the computer awake and app running. [Official scheduled-task behavior](https://developers.openai.com/codex/app/automations).

## Required final behavior

1. A standalone schedule can select multiple owned projects. Each occurrence creates a separate durable run and chat for each selected project. Each run receives that project's instructions, memory scope and approved file bindings. Project roots must never be flattened into one chat.
2. Git projects can run locally or in a newly managed detached worktree. A worktree run uses its generated checkout as its native working directory. Original repository attachments are mapped to corresponding checkout paths, preserving extra explicitly selected context outside that repository. Non-Git projects remain local.
3. Existing-chat follow-ups retain their current context and FIFO ordering. Worktree mode is available for standalone runs; it cannot silently move an existing chat to a new checkout.
4. Task edits capture actual project revisions and file paths from owned records. Account changes, revoked grants, changed projects, cancellation and deleted tasks invalidate preparation and execution. Task limits, model/thinking choices, skills, notification settings and provider selection remain preserved.
5. PostgreSQL stages all project runs atomically and advances the task's next time once. Occurrence uniqueness and active-run constraints must account for project scope. A one-time task completes after all its project runs finish. A failed or uncertain launch is held for inspection and never replayed automatically.
6. Worktree preparation is journaled before any filesystem mutation. A confirmed ready checkout can be reused only for the same not-submitted run after verifying its exact identity and state. An interrupted or uncertain preparation is held. Completed user changes and worktrees are retained for review; cleanup must preserve a recoverable snapshot before removal.
7. Git preparation uses an absolute resolved executable, argument arrays and a bounded environment. It disables hooks, filesystem-monitor commands, submodule recursion and configured external checkout filters. It never runs a repository-supplied executable or invokes a remote fetch during preparation. Linked, protected, replaced or escaped workspace paths fail before execution.
8. New checkout storage uses the configured public output/workspace location on F:. Credentials and preparation journals remain in protected application storage. Generated references remain owned and are checked on every tool/inference boundary.
9. The Scheduled editor exposes project selection and execution mode with the reference's compact advanced settings. Results show their project, checkout and opening/review controls. Existing tasks keep their previous behavior until explicitly edited.
